# AI providers and capability boundaries

Documentation was checked on October 9, 2026. Provider/model availability is verified separately by live tests.

| Provider | Configured model | Catalog combination | Held garment | Credentials |
|---|---|---|---|---|
| Google | `gemini-3-pro-image`, alternative `gemini-nano-banana-2.1` | Person + one/two garment references in one image-editing call | Separate visibility preflight plus image editing; experimental | Attached service account / ADC |
| FASHN | `tryon-max` | One product reference per request; upper then lower sequentially | Unsupported in this adapter | Secret Manager API key |
| Pruna | `p-image-try-on` | Native multiple garment references | Unsupported in this adapter | Secret Manager API key; privacy confirmation required |

Google uses the managed Cloud `generateContent` API at `global`, one result, default 2K, maximum output tokens 8192. Global processing is not constrained to India. The configurable system/catalog/held prompts instruct identity and garment preservation, but quality is empirical and physical fit is not measured. The held workflow first calls `gemini-3.8-flash` for structured visibility/ambiguity checks; unsuitable input ends with recapture guidance. Never use the same held photograph as separate inputs to an incompatible catalog-only API.

Google's dedicated `virtual-try-on-001` is deprecated and is not the initial integration. Current official image model references: [Pro](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-pro-image), [Nano Banana 2.1](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/nano-banana-2-1), [dedicated VTO lifecycle](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/vto/virtual-try-on-001), [data retention](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention).

The POC normalizes stored images to JPEG with a maximum 3,072-pixel edge. The requested 2K default fits within this limit; selecting 4K asks the provider for that size but downloads are still bounded by normalization. The live suite tested 2K only.

FASHN uses `POST /v1/run`, authenticated prediction polling and private base64 inputs/outputs. Adapter settings explicitly use balanced generation with one output and configured resolution; separate clothing items require separate billable attempts. [Try-On Max](https://docs.fashn.ai/api-reference/tryon-max), [privacy/retention](https://docs.fashn.ai/api-overview/data-retention-privacy).

Pruna uses documented authenticated file upload, `POST /v1/predictions` with the `Model` header, polling the persisted prediction ID and guarded image delivery. Provider-uploaded image retention remains independent of application deletion. Its public FAQ describes public generated URLs, and reviewed documents did not establish a precise API image-retention period or blanket no-training promise. It stays blocked for customer photographs until the administrator confirms applicable contractual terms. [API guide](https://docs.api.pruna.ai/guides/models/p-image-try-on), [FAQ](https://docs.api.pruna.ai/faq), [DPA](https://docs.api.pruna.ai/terms-dpa).

Provider availability/configuration checks are not quality tests. Tests mock external operations, while the live benchmark exercises paid Google generation through normal jobs and quota accounting. Text-only/blocked/malformed output is a failure, not a fallback image. Unknown submission outcomes are never automatically regenerated. All generation settings are captured per job; later settings changes apply to new jobs.

Sarees, salwar suits and held-garment inputs remain experimental. Pattern transfer, draping and garment reconstruction can be inaccurate. Faces, hands or body proportions can change; users should inspect outputs before sharing. Results are visual simulations, not measurements or guaranteed representations of retail products.

Saree catalog jobs additionally snapshot category-specific instructions alongside the configured prompts. They prioritize replacing the complete original outfit with a continuous Nivi-style wrap, waist/hip draping, front pleats, ankle-length skirt and shoulder pallu; referenced colors, motifs and borders should continue throughout the drape. A matching opaque blouse is requested when the reference does not show one. Every image-editing job asks for one finished photograph without splits, collages or comparisons. These instructions add no extra inference calls; the immutable snapshot survives later catalog/settings edits. The app displays the generated photograph directly, so the original outfit is no longer overlaid on half the result.

The revised Pro prompt was live-tested on the same fictional adult starting in a T-shirt/trousers and in a synthetic full dress. Both results completely replaced the original clothing with coherent sarees; neither had a half-original split. The two 2K calls reconciled $0.281208 in estimated AI usage. Motif placement/border texture and inferred blouse construction still vary, and one result changed the arm pose. Nano was not rerun for this prompt revision. [Revision quality review](verification/saree-quality-review.json).

The live synthetic comparison produced valid images from both Google models for an ordinary T-shirt, an upper/lower outfit, a saree and a clearly held blouse. Both rejected the same photograph without a held garment. Pro remains the configured default. In this small sample, Nano was cheaper/faster and preserved full-body framing more consistently; Pro's single T-shirt output cropped the legs and changed the expression. Both altered fine motifs, facial details and poses in some cases. This is a single fictional person and one reference per case, so it does not establish a general quality ranking.
