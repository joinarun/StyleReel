# AI providers and capability boundaries

Documentation was checked on October 9, 2026. Provider/model availability is verified separately by live tests.

| Provider | Configured model | Catalog combination | Held garment | Credentials |
|---|---|---|---|---|
| Google | `gemini-3-pro-image`, alternative `gemini-nano-banana-2.1` | Person + one/two garments, with all one-to-six photos per garment, in one image-editing call | Separate processability preflight plus image editing; experimental | Attached service account / ADC |
| FASHN | `tryon-max` | One product image per request; alternate views are composed locally into a sheet; upper then lower sequentially | Unsupported in this adapter | Secret Manager API key |
| Pruna | `p-image-try-on` | Native multiple garment references | Unsupported in this adapter | Secret Manager API key; privacy confirmation required |

Google uses the managed Cloud `generateContent` API at `global`, one result, default 2K, maximum output tokens 8192. Global processing is not constrained to India. The configurable system/catalog/held prompts instruct identity and garment preservation, but quality is empirical and physical fit is not measured. The held workflow first calls `gemini-3.8-flash` for a processability check that supports children, adolescents, and adults. Folds, cropped bodies, imperfect lighting, and incidental people are handled using available evidence; only an explicit inability to identify any intended person or garment stops the job. An inconclusive structured answer continues to image editing with preflight usage still accounted. Provider failures do not automatically instruct users to submit a better photograph. Never use the same held photograph as separate inputs to an incompatible catalog-only API.

Every request includes mandatory image-role instructions even when configured prompts were saved before this revision: the first image supplies the end user's identity, apparent age, body, pose, and background; garment references supply clothing appearance only. A model in a garment photo is never an identity source. Job snapshots group all ordered photo keys by garment, preserving every submitted view across later catalog edits. Google and Pruna receive all individual references; FASHN receives a locally composed multi-view sheet per garment, preserving its separate upper/lower call sequence. The FASHN/Pruna multi-view changes are contract-tested, not live-quality-tested. Google reserves an additional $0.01 per view beyond each garment's first view; Pruna adds one configured unit per additional view. Reported usage is reconciled normally.

The October 11 live Pro 2K checks used a fictional child: one catalog edit with mannequin and different adult-model dress references, and one held blue-shirt workflow including preflight. Both succeeded; visual review found recognizable child identity without copying the reference model, with the dress/shirt appearance reflected in each result. Together they used three provider attempts and $0.283186 reconciled estimated AI spending. Holding poses were lowered and fine drape/button details varied. This small sample validates operation and role handling, not broad identity, child/adolescent quality, or physical-fit guarantees. See the October 11 implementation report for test and authentication limits.

Google's dedicated `virtual-try-on-001` is deprecated and is not the initial integration. Current official image model references: [Pro](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-pro-image), [Nano Banana 2.1](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/nano-banana-2-1), [dedicated VTO lifecycle](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/vto/virtual-try-on-001), [data retention](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/zero-data-retention).

The POC normalizes stored images to JPEG with a maximum 3,072-pixel edge and 7 MiB per image. Before Google submission, the adapter applies a **12 MiB combined raw-image operating budget** (about 16 MiB after base64, plus prompt/JSON overhead) to control memory and bandwidth on the 1 GiB Cloud Run service. This is an application limit, not a claimed Vertex aggregate-request limit. Inputs already within the budget are preserved byte-for-byte. Above the budget, oversized images are resized/recompressed sequentially while preserving aspect ratio, full framing, every view, order, and role labels; no references are discarded and no additional AI inference occurs. Stored catalog originals are unchanged. A regression exercises one person plus twelve reference photos and checks the bounded payload and image-role order. Pruna uploads images individually; FASHN uses one locally composed product image per call.

The requested 2K default fits within the stored-image dimensions; selecting 4K asks the provider for that size but downloads are still bounded by normalization. The live suite tested 2K only.

FASHN uses `POST /v1/run`, authenticated prediction polling and private base64 inputs/outputs. Adapter settings explicitly use balanced generation with one output and configured resolution; separate clothing items require separate billable attempts. [Try-On Max](https://docs.fashn.ai/api-reference/tryon-max), [privacy/retention](https://docs.fashn.ai/api-overview/data-retention-privacy).

Pruna uses documented authenticated file upload, `POST /v1/predictions` with the `Model` header, polling the persisted prediction ID and guarded image delivery. Provider-uploaded image retention remains independent of application deletion. Its public FAQ describes public generated URLs, and reviewed documents did not establish a precise API image-retention period or blanket no-training promise. It stays blocked for customer photographs until the administrator confirms applicable contractual terms. [API guide](https://docs.api.pruna.ai/guides/models/p-image-try-on), [FAQ](https://docs.api.pruna.ai/faq), [DPA](https://docs.api.pruna.ai/terms-dpa).

Provider availability/configuration checks are not quality tests. Tests mock external operations, while the live benchmark exercises paid Google generation through normal jobs and quota accounting. Image-generation text-only/blocked/malformed output is a failure, not a fallback image; inconclusive structured preflight output continues to the image editor. Removing the application's age gate does not alter provider-side safety enforcement. Unknown submission outcomes are never automatically regenerated. All generation settings are captured per job; later settings changes apply to new jobs.

Sarees, salwar suits and held-garment inputs remain experimental. Pattern transfer, draping and garment reconstruction can be inaccurate. Faces, hands or body proportions can change; users should inspect outputs before sharing. Results are visual simulations, not measurements or guaranteed representations of retail products.

Saree catalog jobs additionally snapshot category-specific instructions alongside the configured prompts. They prioritize replacing the complete original outfit with a continuous Nivi-style wrap, waist/hip draping, front pleats, ankle-length skirt and shoulder pallu; referenced colors, motifs and borders should continue throughout the drape. A matching opaque blouse is requested when the reference does not show one. Every image-editing job asks for one finished photograph without splits, collages or comparisons. These instructions add no extra inference calls; the immutable snapshot survives later catalog/settings edits. The app displays the generated photograph directly, so the original outfit is no longer overlaid on half the result.

The revised Pro prompt was live-tested on the same fictional adult starting in a T-shirt/trousers and in a synthetic full dress. Both results completely replaced the original clothing with coherent sarees; neither had a half-original split. The two 2K calls reconciled $0.281208 in estimated AI usage. Motif placement/border texture and inferred blouse construction still vary, and one result changed the arm pose. Nano was not rerun for this prompt revision. [Revision quality review](verification/saree-quality-review.json).

The earlier live synthetic comparison produced valid images from both Google models for an ordinary T-shirt, an upper/lower outfit, a saree and a clearly held blouse. Both rejected the same photograph without a held garment under the earlier stricter preflight; that historical result does not establish the revised all-age processability behavior. Pro remains the configured default. In this small sample, Nano was cheaper/faster and preserved full-body framing more consistently; Pro's single T-shirt output cropped the legs and changed the expression. Both altered fine motifs, facial details and poses in some cases. This is a single fictional person and one reference per case, so it does not establish a general quality ranking.
